Competition Rules

These rules govern team registration, Agent submissions, evaluation integrity, and result verification for the Build-Bench Challenge.

REGISTERING A TEAM OR SUBMITTING AN AGENT CONSTITUTES ACCEPTANCE OF THESE COMPETITION RULES.

Build-Bench is a skills-based software engineering competition. Teams develop repair Agents; organizers run qualified Agent versions on competition Cases and validate each proposed repair through an executable target-architecture build.

The Rules apply together with the versioned Submission Guide, Evaluation Protocol, Timeline, and published data notices. Participants should read those documents before registering or starting an official evaluation.

1. Competition scope

1.1 Competition title

The competition is the Build-Bench Challenge, organized for the ICSE 2027 Competition Track.

1.2 Competition task

A Team submits a runnable software repair Agent. For each Case, the Agent receives the released package materials and build-failure evidence, diagnoses the failure, and modifies the permitted package worktree. The organizer evaluates the resulting change in the official target environment.

1.3 Participant documentation

The Challenge page defines the competition task and released Case sets. The Submission Guide defines the Agent package and runtime interface. The Evaluation Protocol defines Case execution, validation, outcomes, and scoring. The Timeline gives the official competition dates.

2. Team registration and eligibility

2.1 Team registration

  1. Each Team is registered by one Team leader, who provides the Team name and member information through the competition website.
  2. A Team may contain no more than five members, including the Team leader.
  3. An email address is required for every member and may not appear in more than one Team in this competition.
  4. A person may participate through only one Team. Duplicate, misleading, or false registration information may be rejected or investigated.

2.2 Team responsibilities

  1. The Team leader manages the roster, uploaded Agent versions, and selection of versions for official evaluation.
  2. The Team must keep its registration information accurate and complete before the applicable deadline.
  3. Participants are responsible for confirming that their participation and use of third-party materials are permitted by their institution, employer, and applicable licenses.
  4. Any actual or potential conflict of interest involving the organizers must be disclosed through the official support channel.

3. Agent submission and version control

3.1 Conforming Agent bundle

  1. The submitted ZIP must contain a runnable Agent source bundle that conforms to the current Submission Guide, manifest schema, and permitted runtime profile.
  2. The entrypoint must be non-interactive and must complete without organizer or participant intervention.
  3. The bundle must contain only the Agent code, declared dependencies, configuration, and supporting documentation needed to run it.
  4. Secrets, personal credentials, hidden Case information, pre-generated Case repairs, caches, and previous run artifacts must not be included.

3.2 Immutable versions

  1. Every accepted upload creates an immutable Agent version identified by its submission record and content digest.
  2. Any code, dependency, manifest, or configuration change requires a new upload and creates a new version.
  3. A version must pass the platform checks and Hosted Smoke Test before it can be selected for Full Evaluation.
  4. Uploading a version does not automatically start Full Evaluation. The Team must explicitly select a qualified version.
  5. A later upload does not alter an active or completed evaluation snapshot.

3.3 Organizer-run execution

  1. The organizer starts an independent Agent instance for each Case under the published interface and resource policy.
  2. The Agent may read the provided inputs and modify only the permitted worktree and output locations.
  3. The Agent may not directly access the Docker socket, the final Validator, hidden evaluator files, or organizer infrastructure.
  4. Stdout, stderr, declared result files, and platform events may be retained for diagnosis, auditing, and reproducibility.

4. Competition data, models, and tools

4.1 Competition materials

  1. Released Cases, schemas, examples, logs, and Starter Kit materials may be used for participation subject to their published licenses and data notices.
  2. Participants must preserve applicable copyright, attribution, redistribution, and open-source license obligations.
  3. Unreleased Cases, hidden evaluator assets, and confidential organizer materials may not be obtained, used, shared, or redistributed.

4.2 Models, external data, and tools

  1. Teams may develop Agents using language models, prompting, retrieval, code search, static analysis, log processing, and other repair tools that comply with the published runtime and network policy.
  2. External models, datasets, knowledge bases, APIs, and tools must be lawfully accessible to the Team and disclosed as required by Section 8.
  3. Use of a third-party service does not transfer responsibility for compliance, reproducibility, cost, availability, or licensing to the organizers.
  4. Participants must not embed API keys or personal credentials in an Agent bundle. Any organizer-managed credential mechanism will be described separately if external calls are permitted.

5. Evaluation and scoring

5.1 Per-Case validation

  1. The organizer runs the frozen Agent version on a Case and derives a canonical patch from the modified worktree.
  2. The platform checks that patch for allowed paths, required structure, and prohibited build-bypass behavior.
  3. The canonical patch is applied to a clean copy of the Case and rebuilt in the official target-architecture environment.
  4. A repair is not compared textually with a reference patch. It succeeds only when the clean target build and expected artifact validation succeed.

5.2 Outcomes

  1. Agent errors, no-fix outcomes, build failures, dependency-resolution failures, timeouts, and invalid patches are unsuccessful Case outcomes under the final Evaluation Protocol.
  2. A verified organizer infrastructure error is not treated as a participant repair failure. The affected Case or evaluation may be retried or recovered under the published correction procedure.
  3. No partial official score is published while unresolved infrastructure errors prevent the aggregate result from being finalized.

5.3 Primary metric

Build Success Rate is the primary ranking metric: the number of successfully repaired Cases divided by the official evaluation denominator. The final denominator definition and any tie-breaker will be published with the frozen Evaluation Protocol.

6. Prohibited conduct

Participants must not obtain an advantage by bypassing the repair task, evaluator, resource policy, or Team-registration rules.

  1. Do not embed hidden solutions, leaked labels, Case-specific lookup tables, pre-generated repair patches, or other undisclosed answers in the Agent or its dependencies.
  2. Do not exploit or attempt to escape the Agent runtime, Build Gateway, Validator, sandbox, authentication system, storage, scheduler, or network controls.
  3. Do not suppress failures, delete essential tests, replace the package with a dummy artifact, or disable meaningful functionality merely to obtain a successful build result.
  4. Do not alter immutable Case inputs, manifests, checksums, hidden metadata, evaluator files, result records, or any path outside the permitted worktree.
  5. Do not use undeclared manual, remote, or third-party intervention to make Case-by-Case decisions during organizer-run evaluation.
  6. Do not use multiple Teams, accounts, identities, or automated requests to evade registration, submission, evaluation, or resource limits.
  7. Do not run unrelated workloads, mine cryptocurrency, interfere with other participants, or attempt to degrade competition services.

7. Hidden evaluation and confidentiality

  1. Hidden evaluation Cases remain under organizer control and are not distributed before final evaluation.
  2. Official hidden evaluation uses a frozen Agent version, Case-set version, runtime image, Validator image, and protocol version.
  3. Teams may use only the feedback intentionally released by the platform and must not probe the service to infer hidden Case contents, labels, reference repairs, or evaluator internals.
  4. Organizers may inspect successful, unusually small, suspicious, or policy-sensitive repairs and may rerun an entry to verify its result.
  5. Any accidental exposure of hidden or confidential material must be reported promptly and must not be used or shared.

8. Method disclosure and reproducibility

8.1 Required disclosure

A final entry must describe the system that produced its result. The disclosure must identify, as applicable:

  1. base model names, providers, and versions when available;
  2. major prompt templates or prompting strategy, repair-loop design, retrieval sources, static analyzers, and external tools;
  3. training, fine-tuning, external datasets, private knowledge bases, and pre-processing used by the entry;
  4. third-party APIs or services contacted during execution; and
  5. known nondeterminism, caching, dependency, and reproducibility constraints.

8.2 Verification materials

  1. Teams must retain the submitted source, lockfiles, configuration, and method documentation needed to explain and rerun the evaluated version.
  2. Organizers may request logs, configuration details, or a reproducibility demonstration for result review.
  3. Any public solution description or solution paper must correspond to the Agent version that produced the reported official result.

9. Review, correction, and enforcement

  1. A malformed or nonconforming Agent, output, or patch may be rejected or recorded as unsuccessful under the Evaluation Protocol.
  2. When an organizer-controlled infrastructure defect affects an evaluation, organizers may correct the defect and rerun the affected work under a documented procedure.
  3. Organizers may request clarification or verification when an entry is unreproducible, incomplete, anomalous, or potentially noncompliant.
  4. A result may be corrected, withheld, or removed when it cannot be verified or when the Team fails to provide required disclosure or reproducibility materials.
  5. Deliberate hidden-answer use, build bypass, evaluator exploitation, credential abuse, false registration, or other serious misconduct may result in disqualification and removal from the leaderboard.

10. Versioned rules and pending parameters

Several operational values require pilot measurements and organizer approval. Before public evaluation opens, the organizers will publish and version the following:

  1. upload, Hosted Smoke Test, and Full Evaluation frequency limits;
  2. Case-level Agent and build timeouts, CPU, memory, storage, and build-feedback budgets;
  3. network access, external API, and organizer-managed credential policies;
  4. the official scoring denominator, tie-breaker, feedback visibility, cancellation, rerun, and correction procedures; and
  5. any remaining eligibility, conflict-of-interest, or final-result verification procedures required by the ICSE Competition Track.

Material updates will carry a version and publication date. The Timeline page governs competition dates, and the frozen Evaluation Protocol governs official scoring.
