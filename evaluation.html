Evaluation Protocol

This page explains what happens after you select a qualified, immutable Agent version for evaluation: how the platform runs it, validates each repair, records outcomes, and produces a score. For packaging and upload instructions, see the Submission Guide.

Core principle

What counts as a successful repair?

A repair succeeds only when the platform can generate a valid canonical patch, apply it to a clean copy of the Case, and build the expected package artifacts on the target architecture under the official Validator.

The repair does not need to match an organizer reference patch. A different change receives credit when it respects the published policy and produces a genuine successful build.

Primary metric: Build Success Ratesuccessful Cases ÷ evaluated Cases

Per-Case protocol

How each Case is evaluated

Each Case is an independent run. One slow or unsuccessful Case does not stop other scheduled Cases, and the selected Agent archive remains immutable throughout the evaluation.

  1. Freeze the run inputs.

    The platform records the Agent archive and its checksum together with the Case-set, runtime, Validator, and protocol versions.

  2. Prepare a clean Case.

    The Case checksum is verified and an isolated writable worktree is created from the original package materials.

  3. Run the Agent.

    The declared entrypoint receives the standard workspace and runs under the published time, resource, network, and build-feedback policy.

  4. Generate the canonical patch.

    After the Agent exits, the platform validates agent-result.json and derives repair.diff from the original and modified worktrees.

  5. Audit the repair.

    The canonical patch is checked for forbidden paths, policy violations, and build-bypass behavior described in the Rules.

  6. Rebuild from clean inputs.

    The platform reapplies the canonical patch to a fresh Case and invokes the official Docker Validator for the target architecture.

  7. Record the outcome.

    Agent status, Validator status, duration, patch statistics, and permitted logs are stored as structured evidence.

Case results

How outcomes are handled

The platform records Agent execution and final build validation separately. An evaluation can complete normally even when many Cases are unsuccessful; an evaluation-level System Error is reserved for organizer-controlled failures.

OutcomeWhat it meansEvaluation treatment
succeededThe audited patch produces the expected package artifacts in the clean target build.Successful Case.
failed, unresolvable, or no_fixThe target build fails, dependencies cannot be resolved, or the Agent proposes no allowed change.Unsuccessful Case result.
agent_errorThe Agent crashes, exits abnormally, or omits a valid agent-result.json.Unsuccessful Case result.
timeoutThe Agent or its permitted build work exceeds the applicable Case-level limit.Unsuccessful Case result.
invalid_patchThe canonical repair cannot be applied or violates path, output, or repair policy.Unsuccessful Case result.
infrastructure_errorAn organizer-controlled Worker, storage service, runtime, or Validator fails independently of the Agent repair.No partial score is published; the affected evaluation is reviewed or rerun.
Ranking

How scoring works

Build Success Rate is the primary ranking metric. The platform freezes an aggregate score only after all Cases have terminal outcomes and any organizer infrastructure errors have been resolved. A completed evaluation therefore reports both the number of successful Cases and the total number of evaluated Cases.

Diagnostic information explains where time and failures occurred; it is not combined into a weighted score.

  • Case outcomes grouped by result category
  • Agent runtime and final build duration
  • Patch size, modified-file count, and policy validation status
  • Build requests, retries, iterations, and model or tool usage when collected
  • Case-set, runtime, Validator, and protocol versions used for the run
Competition phases

Evaluation stages and feedback

The same Agent interface is used across stages, but the Case set, purpose, and visible feedback differ.

StagePurposeVersion and feedback
Hosted Smoke TestCheck the uploaded bundle, entrypoint, dependencies, workspace behavior, and output contract on a small lightweight set.Runs the uploaded immutable version and returns detailed qualification diagnostics. It does not produce an official score.
Full Evaluation during the public phaseMeasure repair performance on the versioned validation set and produce the public evaluation result.Starts only after the team selects a qualified immutable version. Progress and the completed aggregate result appear in My Submissions.
Hidden final evaluationEvaluate the team's frozen final Agent on organizer-controlled held-out Cases.Uses the frozen Agent, Case set, runtime, Validator, and protocol versions. Aggregate results and permitted diagnostics are released after the deadline.
Versioned release

Rules to be published before evaluation opens

To be announced in the final Evaluation Protocol.

The organizers will publish the exact score-denominator and cancellation semantics; any tie-breaker; Agent and build timeouts; build-feedback, iteration, and tool-call budgets; CPU, memory, storage, concurrency, network, and credential policies; submission frequency and rerun rules; and the feedback visible during public and hidden evaluation. Current pilot settings do not define these competition limits.

See Rules for integrity, disclosure, and enforcement requirements, and Timeline for the publication and evaluation schedule.
