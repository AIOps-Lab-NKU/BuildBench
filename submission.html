Agent submission

Agent Submission Guide

Submit a runnable Agent source bundle. The platform starts one isolated instance for each Case. The Agent modifies its worktree and may request a limited number of build-feedback runs. When the run ends, the platform creates the canonical repair.diff, and the Docker Validator verifies it on a clean Case.

01 / Start

Quick start

Run the official example first, then create, test, package, and upload your own Agent.

  1. 01
    Get the Starter Kit

    Download the archive from Data & Downloads, extract it, and enter the project directory.

    tar -xzf buildbench-starter-kit.tar.gz
cd buildbench-starter-kit

    Expected: the current directory contains bb, agents/, and example-cases/.

  2. 02
    Run the official demo

    Check Git, Docker, and the versioned images, then run the complete failure-to-success example.

    ./bb doctor
./bb demo

    Expected: Final validation succeeded; evidence is saved under runs/demo/.

  3. 03
    Create your Agent

    Copy the managed Python template into a new editable Agent directory.

    ./bb init my-agent

    Expected: a new Agent is created at agents/my-agent/; existing directories are never overwritten.

  4. 04
    Edit src/ and test locally

    Implement the repair logic in agents/my-agent/src/, then run every bundled Example Case.

    # Edit agents/my-agent/src/main.py
./bb test --agent ./agents/my-agent

    Expected: per-Case patches, logs, and validation results are written under runs/tests/my-agent/.

  5. 05
    Check and package

    Validate the manifest, entrypoint, dependencies, and files before creating a deterministic upload bundle.

    ./bb check --agent ./agents/my-agent
./bb package --agent ./agents/my-agent

    Expected: both checks pass and the command prints the ZIP path, size, and SHA-256.

  6. 06
    Upload the Agent bundle

    Open My Submissions, choose Make new submission, and upload the generated ZIP.

    ls -lh dist/agent-submission.zip

    Expected: a new immutable Agent version appears in the submission table and enters the Checking state.

02 / Package

Submission contents

Upload one ZIP archive with a shallow, inspectable root. The platform reads the manifest before building the Agent runtime.

agent-submission.ziparchive root
agent-submission.zip
├── agent.yaml
├── src/
├── requirements.lock
├── Dockerfile
├── tests/
│   └── smoke/
└── README.md
agent.yaml and src/
Required. Declare the runtime and include the Agent implementation.
requirements.lock
Required when using the managed Python runtime.
Dockerfile
Include only when using a custom runtime.
tests/ and README.md
Optional local tests and method documentation.
Do not include secrets or evaluation answers.

Exclude .env files, API keys, pre-generated patches, hidden Case information, caches, and runtime artifacts.

Minimum agent.yaml

The manifest declares how the platform builds and starts the Agent. The complete schema will be provided in the Starter Kit.

agent.yamlminimum managed-runtime example
schema_version: "0.1"

agent:
  name: "example-agent"
  version: "1.0.0"

runtime:
  type: "managed"
  profile: "python-3.11"

entrypoint:
  - "python"
  - "-m"
  - "src.main"

protocol:
  version: "0.1"
  build_feedback: true
03 / Runtime

Runtime interface

Each Case starts in a fresh workspace. The original input remains unchanged while the Agent works on a writable copy.

Workspace

/workspaceone Case run
/workspace/
├── input/            # read-only
├── work/
│   └── repo/         # writable
└── output/           # writable
  • Read input/.It contains the task metadata, initial failure evidence, and original package tree.
  • Modify only work/repo/.This is the candidate package tree used for build requests.
  • Use stdout and stderr for logs.The platform captures both streams for diagnostics.
  • Optionally write agent-result.json.Place machine-readable completion details in output/.

Build feedback

When build feedback is enabled, the Agent requests a build through the platform-provided bb-build command. This planned CLI will be included in the Starter Kit.

04 / Test

Test your submission

Test the exact Agent version you intend to evaluate. Local checks catch packaging errors; the hosted Smoke Test checks that the same bundle can run under the competition protocol.

Before full evaluation

Complete these checks in order before using a full-evaluation attempt:

  1. Prepare the released tools.Download the Starter Kit, schemas, and development Cases from Data & Downloads when they become available.
  2. Run local conformance checks.Validate the ZIP layout and agent.yaml, then start the declared entrypoint in the local Runner.
  3. Exercise the runtime interface.Run at least one example Case, edit only /workspace/work/repo, and verify any agent-result.json output.
  4. Pass a hosted Smoke Test.Upload the same Agent bundle from My Submissions and review the returned logs and diagnostics.
  5. Select the qualified version.Start full evaluation explicitly; uploading a new version alone does not place it in the evaluation queue.

Testing locally

Local testing should confirm that the submission contract works before organizer resources are used. Check all of the following:

  • The ZIP opens with agent.yaml and src/ at its root.
  • The manifest matches the published Agent Schema and declares one valid entrypoint.
  • The entrypoint starts without interactive input and exits with a meaningful status.
  • /workspace/input remains unchanged; repository edits are confined to /workspace/work/repo.
  • Optional agent-result.json output matches the published result schema.
  • The Agent completes at least one released example or local Smoke Case.

PlannedThe Starter Kit will provide the local Runner, conformance CLI, schemas, example Cases, and exact commands. These downloads are not yet published.

Smoke tests

A hosted Smoke Test uses the same Agent Runner, workspace layout, build-feedback protocol, and status schema as formal evaluation, but runs only a small set of lightweight public Cases. It is intended to expose missing dependencies, invalid entrypoints, permission errors, and malformed output before a full evaluation.

Smoke Test results include more detailed logs and diagnostics than the leaderboard. They do not contribute to the official score, and passing a Smoke Test does not guarantee success on the full Case set.

Full evaluation

Uploading an Agent creates a versioned submission but does not automatically start full evaluation. After that version passes format checks and the required Smoke Test, select it in My Submissions and choose Start evaluation. The platform then creates one isolated Agent job per Case and schedules jobs subject to the published resource policy.

For each Case, the platform records the Agent outcome separately from the final Docker Validator outcome. Only the canonical patch generated from the Agent's worktree is reapplied to a clean Case for the official target-architecture build.

05 / Requirements

Submission requirements

A submission must be reproducible, non-interactive, and safe to run against organizer-controlled Cases. Requirements that are still under infrastructure review are marked TBA.

Key requirements checklist

  • Submit one source ZIP containing the required agent.yaml and src/ entries.
  • Declare one runtime: managed Python 3.11 with requirements.lock, or a custom runtime with a platform-reviewed Dockerfile.
  • Provide a deterministic, non-interactive entrypoint that can process one Case per invocation.
  • Do not include .env files, credentials, API keys, pre-generated repair patches, hidden Case information, dependency caches, or previous run artifacts.
  • Read task metadata and the original package only from /workspace/input; make all proposed repairs in /workspace/work/repo.
  • Do not modify evaluator files or paths outside the Case's published allowed_paths.
  • Only optional machine-readable status and diagnostics may be written to /workspace/output. The official repair.diff is generated by the platform, not the Agent.

Runtime and security

  • The Agent runs as a non-root user in an isolated runtime created for one Case.
  • /workspace/input is mounted read-only; only the work and output directories are writable.
  • The Docker Socket and Docker daemon are never exposed to the Agent.
  • Build feedback is requested through the platform-provided bb-build command and Build Gateway. The Docker Validator remains organizer-controlled.
  • The platform captures stdout, stderr, exit status, wall time, and build requests for diagnosis and audit.
  • Network policy, per-Case wall-time limit, maximum build requests, CPU, memory, and storage limits are TBA.

Dependencies and custom runtime

For the managed runtime, declare Python dependencies in requirements.lock. The competition will publish the exact Python 3.11 base environment and supported installation process with the Starter Kit. Undeclared host packages must not be assumed.

A custom Dockerfile is optional for Agents that cannot use the managed runtime. The platform will inspect it, build an immutable image, record its digest, and run it under the same non-root, filesystem, network, and resource policies as managed submissions.

Supported base images, package-installation rules, network access during image construction and execution, maximum ZIP size, and submission frequency are TBA. Final values will be published before submissions open.
